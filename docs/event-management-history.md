# Owner event management history

The owner management screen keeps upcoming events and history separate. No records are deleted by this feature, and existing public and legacy owner endpoints retain their contracts.

- `GET /api/v1/venue-owner/events/venue/{venueId}/management` returns a `BaseResponse` containing `upcomingEvents` (existing event DTOs), `pastCount` (a database count, not loaded cards), and `historyAsOf` (UTC ISO instant).
- Opening history requests `GET .../history?asOf={historyAsOf}&size=20`. The response contains `items`, `nextCursor` and `hasNext`. Further requests send the same `asOf` and the returned opaque cursor. Size is 1–50, default 20. No continuation is returned on the last page.
- Both endpoints require the venue role and independently verify the current venue owner. Responses use `Cache-Control: private, no-store`. Cursor payloads are bounded (512 characters) and scoped to the venue and cutoff; a cursor is a position, not permission.
- The cutoff uses the server clock and Europe/Istanbul event wall time. The effective end matches the app: minute precision, missing/earlier end falls back to start plus one hour, missing start falls back to 23:59:59, and exact end equality is still upcoming. A fixed cutoff prevents ongoing events from changing history membership halfway through pagination. It is not a cross-request database snapshot: deliberate edits/new past events may be reflected on refresh.
- History queries select at most `size + 1` positions in SQL, ordered by event date, start time and UUID descending. Only the requested page is hydrated/mapped, including batched poster resolution. Keyset positions continue correctly when earlier rows or the cursor row have been deleted.
- The management response count and upcoming cards share a repeatable-read transaction; each history page does likewise. Future/current events remain loaded together for the existing weekly/future sections.

The native read mirrors the active Hibernate time mapping before comparing or ordering times. In the existing application, `hibernate.jdbc.time_zone=UTC` and a non-UTC JVM can store a `LocalTime` shifted through `java.sql.Time`'s 1970 reference date. Applying today's zone offset, or treating raw SQL time as the DTO time, would move events into history too early. The adapter derives this conversion from the actual entity JDBC mapping and configured JDBC calendar; it never rewrites event times or changes global timezone configuration.

Apply `scripts/db/2026-09-21-event-management-history.sql` in autocommit before enabling the new UI. It adds an online partial venue/date/start/UUID index. Dates earlier than yesterday are counted using an indexed range; only yesterday/today require normalized end-time comparison. Upcoming reads prune older dates, and history uses an indexed date range before the normalized keyset sort and SQL limit. The index deliberately contains no deployment-specific timezone expression. `CREATE INDEX CONCURRENTLY` must not be wrapped in a transaction. The local dev migration list includes it. No data cleanup accompanies it.

Focused tests are `EventManagementServiceTest`, `EventManagementControllerTest`, `EventManagementRepositoryPostgresTest`, and `EventManagementHibernatePostgresTest`. Disposable PostgreSQL 16 tests validate the actual time semantics, deletion-safe keyset, bounded results, repeatable online migration, and the normalized production SQL's date-index plan. The Hibernate roundtrip tests explicitly combine an Istanbul JVM with UTC JDBC storage (raw 18:00 / entity 20:00), verify midnight wrapping/fallback and confirm the UTC JVM path needs no shift. Run in the existing isolated verification build lane so the IntelliJ application's classpath is untouched.

Local acceptance on 2026-09-21 passed 43 backend tests (the four management suites plus the existing EventRepositoryTest), 133 Flutter widget/navigation tests, 97 repository/model tests and 10 read-only live API assertions. Physical-device acceptance covered history expansion/collapse, tab roundtrip, refresh and event-detail return. All six existing event rows, three plan rows and fifteen occurrence rows retained their original full-row hashes. The index was applied successfully to the local database and the refreshed backend reported health UP. These checks do not constitute a production deployment or a concurrent-user load test.
