# Video transcode resource safety

Untrusted video is admitted in two bounded stages. The object is downloaded to
an isolated temporary workspace, then one timeout-limited `ffprobe` process must
return complete duration, resolution and frame-rate metadata. Any probe error or
missing/invalid field rejects the job before the first FFmpeg process starts.

`VideoTranscodeResourceValidator` then enforces:

- maximum duration: 900 seconds;
- maximum dimension: 3840 pixels and maximum pixel count: 8,294,400;
- maximum frame rate: 60 fps;
- conservative HLS output estimate from every configured ladder video/audio
  bitrate, multiplied by 1.20 plus 16 MiB fixed overhead;
- maximum estimated output: 2 GiB;
- maximum source plus estimated-output working set: 6 GiB;
- actual usable temp space must cover the estimate plus a 512 MiB reserve.

The verified video source download has its own two-hour, environment-configured
AWS request/attempt deadline (`SOUNDCONNECT_TRANSCODE_SOURCE_DOWNLOAD_TIMEOUT_SECONDS`).
It is applied only to the large transcode download request; verification
HEAD/COPY/signature reads and image downloads retain the short 30-second storage
deadline. The deletion producer-safety calculation includes the full video
download deadline.

Insufficient free space or a timed-out global reservation is a retryable
`TranscodeCapacityUnavailableException`; it must not classify the verified
source as permanently invalid. Invalid/missing media metadata and policy-limit
violations remain permanent `VideoTranscodeRejectedException` failures.

Each FFmpeg variant additionally has two independent `-t` duration caps plus
VBV `-maxrate`/`-bufsize` limits. While a native process is running, the worker
measures real generated bytes and the complete workspace every second and
terminates the child immediately on overflow. It repeats the measurement after
every variant, the master playlist and the thumbnail before the next encode or
upload. This closes the gap between a conservative estimate and
crafted/inconsistent container metadata.

Jobs reserve `maxTempWorkBytes` from a process-wide byte budget before the
source download. The reservation is held through upload/finalization and temp
cleanup. Current listener concurrency and native worker threads are both fixed
at one; production validation also requires
`globalTempBudgetBytes >= maxTempWorkBytes` and
`tempVolumeBytes >= globalTempBudgetBytes`.

All limits are environment-configurable through the
`SOUNDCONNECT_TRANSCODE_*` variables documented in `.env.example`. Invalid
ladder bitrates fail closed so a configuration error cannot silently
underestimate resource usage.

## Runtime isolation

The Compose API and native worker are separate targets. Only the worker image
contains FFmpeg. It is read-only, drops Linux capabilities, enables
`no-new-privileges`, limits CPU, memory and PIDs, and provides a bounded
`/tmp` tmpfs for native media work. `dev.cmd idea` stops both Compose
application processes, so these container limits do not change the normal
IntelliJ backend workflow.

`media.transcode.worker.enabled` conditionally creates the video listener and
its manual-ack container. The production API profile defaults this switch to
false and fails startup if an external override enables it. Native child
processes receive a small allowlisted environment, so JWT, database, mail and
object-storage secrets are not inherited.

The same boundary covers public image variants. Every event listener,
dispatcher, scheduler, executor, thumbnail service and native image processor
is conditioned on `media.image-variants.worker.enabled`. Local development
sets it true; the production API forces it false. Image FFmpeg and its ffprobe
child use the same environment sanitizer. Enabling either native worker on a
production API node is a startup error.

## Dedicated production worker

Native production work runs only from `soundconnect-media-worker.jar` and its
explicit no-web Spring context. The production API continues to reject
`prod,transcode-worker`, `prod,image-worker`, and `prod,media-worker`: adding a
profile to the API artifact can never turn it into a worker. The dedicated
artifact starts with `prod,media-worker` and rejects API secrets or shared
DB/Rabbit identities.

The worker has a separate consume-only Rabbit identity, a column-limited media
database role, a generated-object/source-read-only S3 workload role, DB+Rabbit
readiness, and one native job per 6 GiB volume. Exact grants, IAM policy,
network-policy gate, rollout order, and executable boundary checks are in
[`IsolatedMediaWorker.md`](IsolatedMediaWorker.md).

Container limits remain defense in depth, not a replacement for application
preflight, least-privilege service identities, or the production egress policy.
